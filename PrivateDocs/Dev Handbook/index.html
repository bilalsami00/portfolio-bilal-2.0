What this portfolio is

This repository is the personal portfolio website of Muhammad Bilal Sami, a Frontend Developer at Maze Digital in Karachi. It is a Next.js 13.1.6 application written in TypeScript and styled with Tailwind CSS, deployed on Vercel at https://bilalsami.vercel.app.

It has two audiences:

  • Public visitors (recruiters, clients, engineers) see five pages: Home, Projects, About, Contact, and a custom 404 page.
  • The owner signs into a hidden admin area called Mission Control at /mission-control to read contact-form messages and anonymous visitor sessions stored in Firebase Firestore.

Where the code came from

The folder name OpenFolio-main, the storage keys prefixed openfolio:, and the Firebase app name "openfolio-admin" show the project began from an open-source template called OpenFolio. Git history starts with "first commit" on 2026-09-15 and includes "Rebrand portfolio to Bilal Sami and remove legacy ownership residue". Some template-era files remain unused; they are listed in Chapter 2.

What it was built to accomplish

The original brief is not written down in the repository. Based on the code and its comments, the site does four jobs:

  1. Present a verified professional profile. Comments in data/site.ts say facts follow "the 2026-10-18 verified profile" and that "unconfirmed claims stay off the site". The testimonials list in data/testimonials.ts is deliberately empty so no fake quotes appear.
  2. Showcase ten Maze Digital case studies with screenshots, technologies, live links, and honest notes about what is incomplete in each product.
  3. Accept contact messages that are stored in Firestore and optionally emailed to the owner.
  4. Give the owner insight into who visits, through a small, self-built, privacy-conscious visitor tracker (no Google Analytics or other third-party analytics).

How the major systems connect

  1. Buildnext build turns every page plus the data/ content into static HTML and JS bundles.
  2. First loadThe visitor gets HTML instantly; the inline script in _document applies the saved theme.
  3. HydrationReact attaches; _app mounts theme, nav, shortcuts, Lenis, and the visitor tracker.

  5. Server callsOnly the contact form and the visitor tracker call /api/*, which write to Firestore.

Chapter 3 · Application Core

Framework and Application Fundamentals

What Next.js does for this project, how pages are rendered, how the application starts, and — most importantly — which of the two Next.js routers this repository uses and why that matters.

What Next.js is

React is a library for building user interfaces out of components. It does not decide how URLs map to screens, how pages are built into files, or how server code runs. Next.js is a framework built on React that adds exactly those things:

  • File-based routing — a file at pages/about.tsx becomes the URL /about.
  • Pre-rendering — pages are turned into HTML ahead of time, so visitors and search engines see content before JavaScript runs.
  • API routes — files in pages/api/ become server endpoints (serverless functions on Vercel).
  • Build tooling — TypeScript compilation, CSS processing (Tailwind via PostCSS), code splitting, and minification with no manual Webpack setup.

How the application starts

Two special files wrap every page:

  1. pages/_document.tsxRenders <html lang="en" data-theme="dark">, runs the inline theme script, preloads two fonts. Server/build only.
  2. pages/_app.tsxWraps the current page in ThemeProvider, the atmosphere div, nav, footer, and global behaviours.
  3. getLayoutIf the page defines one (Mission Control does), it wraps the page in an extra layout.
  4. Page componentFor example HomePage, which renders PageShell and its sections.

Four of those children render nothing visible (SmoothScroll, PathMemory, VisitorTracker, and KeyboardShortcuts until ? is pressed). They are components only so they can use hooks and subscribe to router events for the whole app lifetime.

_app.tsx also imports styles/globals.css (the only place global CSS may be imported in the Pages Router) and sets config.autoAddCss = false for Font Awesome after importing its stylesheet, which prevents icon size flashes on load.

App Router versus Pages Router

Next.js has two routing systems. They can technically live side by side, but each project usually commits to one.

The Pages Router

The original system. Each file in pages/ is a route. One global wrapper (_app) and one HTML shell (_document) apply to all pages. Components run on the server (for pre-rendering) and then in the browser. Data is loaded with special exported functions such as getStaticProps. API endpoints live in pages/api/.

The App Router

Introduced in Next.js 13 and marked stable in 13.4. Routes are folders in app/, and the page is the page.tsx inside. Each folder can have its own layout.tsx, loading.tsx, and error.tsx, and layouts nest. Components are React Server Components by default; anything that uses state, effects, or browser APIs must start with "use client". Data is fetched with async components and fetch. API endpoints are route.ts "route handlers".

Which router this repository uses

Answer: the Pages Router only

There is no app/ directory. All routes are in pages/.

Evidence you can point to:

  • pages/_app.tsx and pages/_document.tsx exist — these are Pages Router concepts.
  • Pages are typed as NextPage or NextPageWithLayout (utilities/pageLayout.ts).
  • Components import useRouter from next/router and subscribe to router.events (nav, SmoothScroll, PathMemory, VisitorTracker).
  • Metadata uses next/head in components/layout/index.tsx.

Server Components and Client Components here

Because this is the Pages Router, the Server/Client Component split does not apply. Every component is an ordinary React component that runs twice: once in Node.js during next build to produce HTML, and again in the browser to hydrate. That is why browser-only code is always inside useEffect (for example localStorage in ThemeProvider) or guarded with typeof window (getClientApp in utilities/firebaseClient.ts).

Do not confuse the server/ folder with Server Components. server/ is ordinary Node.js code that only API routes import.

Why the current architecture fits

The original reason for choosing the Pages Router is not documented. The template the project started from used it. Observed benefits for this codebase:

  • Small, fixed set of routes with no per-request data — static pre-rendering is ideal, and the Pages Router does it with zero configuration.
  • Global behaviours rely on router.events (closing the menu on navigation, scroll reset, visitor page tracking, the 404 "Go back" memory). The App Router has no equivalent event API.
  • Almost every component is interactive (hooks, portals, observers). In the App Router most would need "use client", reducing the benefit of Server Components.
  • The one place needing a nested layout (Mission Control) is covered by the documented getLayout pattern.

What migrating to the App Router would mean

It is not necessary today. Consider it only if you need something the Pages Router cannot do well — for example many data-driven routes with per-route loading states, streaming, or a large amount of non-interactive content where Server Components would cut JavaScript.

What a migration would involve:

  1. Upgrade Next.js (13.1.6 → at least 13.4, realistically the current major), which also means upgrading eslint-config-next and probably React.
  2. Replace _app.tsx/_document.tsx with app/layout.tsx; move the theme script and font preloads there.
  3. Replace every next/head usage in PageShell with the metadata export per route.
  4. Rewrite all router.events listeners (four components) using usePathname + useEffect; there is no routeChangeStart.
  5. Add "use client" to every component using state, effects, refs, portals, or browser APIs.
  6. Replace getLayout with app/mission-control/dashboard/layout.tsx.
  7. Optionally move pages/api/* to route.ts handlers (they can stay in pages/api during a gradual migration).

Compatibility risks

Scroll restoration and the mobile-menu focus logic depend on Pages Router event timing; the 404 page's HTTP status and MaskedNotFound behaviour would need notFound(); Lenis and Font Awesome need client boundaries; and Firebase client code must never be imported by a Server Component.

React Components and Component Architecture

How React components, props, state, and hooks work — explained through this portfolio's own components — and where to go to change each visible part of the site.

What a React component is

A component is a function that takes inputs (props) and returns a description of UI (JSX). React calls the function, compares the result with what is on screen, and updates only what changed. ESLint in this repo requires components to be arrow functions.

That is the whole component: a typed props object, a default value, and JSX. It is used for technology pills on project cards, the modal, the experience timeline, and About.

Props and composition

Big UI is built by composing small components. A typical Home section:

  • Container provides the max width (72rem) and responsive side padding.
  • SectionHeading provides the eyebrow, accent mark, title, and description.
  • RevealOnScroll wraps any content in a fade-and-slide entrance.
  • The list is rendered with .map() over data from data/site.ts; each item has a stable key (its id).

The children prop is what lets Container and RevealOnScroll wrap anything. Default props are used heavily: ContactCtaBanner has default eyebrow/title/description, and pages override them (Projects passes "Questions about this work?").

State and event handlers

State is data a component remembers between renders; changing it re-renders the component. The Projects page is the clearest example:

  1. Clicking a filter button runs onClick={() => setActiveFilter(category)}.
  2. React re-renders; useMemo recomputes the filtered list only because activeFilter changed.
  3. Each ProjectCard receives onSelect={setSelectedProject}. When a card is clicked it calls onSelect(project) — this is how a child talks to its parent: through a callback prop.
  4. selectedProject becomes non-null, so ProjectDetailsModal renders. Its onClose sets it back to null.

The same pattern (local selectedProject state + modal) is repeated independently in components/home/HomeFeaturedProjectsSection.tsx.

Controlled versus uncontrolled inputs

A controlled input gets its value from React state and reports changes through onChange; React is the source of truth. An uncontrolled input keeps its own value in the DOM and is read later with a ref.

Every input in this repository is controlled:

  • Contact form fields use Formik: value={formik.values.email} + onChange={formik.handleChange}.
  • The honeypot field on the contact form uses its own useState.
  • The admin login form (components/admin/AdminLoginForm.tsx) uses useState for email, password, remember-me, and show-password.

Tailwind configuration and design tokens

tailwind.config.js scans pages/, components/, and data/ for class names, and extends the default theme with theme.json:

  • sm is 425px here, not Tailwind's default 640px. xs (375px) is added. Read sm: classes as "larger phones and up".
  • The palettes are named by role in the dark design: ink = backgrounds, parchment = text, crimson = accent, steel = muted text and borders. primary (teal) is defined but no component class uses it; light mode uses hard-coded teal values in CSS instead.
  • Because data/ is scanned, class names written inside data strings would also be kept by Tailwind.

CSS variables (theme tokens)

The top of styles/globals.css defines variables twice: once for :root, html[data-theme="dark"] and once for html[data-theme="light"].

Components rarely read variables directly; the reusable classes do (.btn-primary uses var(--btn-primary-bg, var(--color-accent))). Inline styles that need the accent use var(--color-accent) or var(--color-accent-glow), so they follow the theme automatically.

The "polish token" reset

Some newer variables (--color-accent-text, --btn-primary-bg, --focus-ring, --band-bg…) are reset to initial inside [data-surface="mission-control"] and inside every form. Rules always provide a fallback (var(--btn-primary-bg, var(--color-accent))), so forms and the admin area keep the original look while public pages get the refined palette. If a colour change "does not apply" inside the contact form, this is why.

How light mode actually works: class remapping

This is the most important styling concept in the repository. Components are written with dark-theme classes (text-parchment-100, bg-ink-900, border-steel-700, text-crimson-300). Light mode does not change the JSX; instead, the bottom of globals.css overrides those exact classes when data-theme="light":

Only listed classes are remapped

If you use a palette class that is not in the remap list — for example text-parchment-600 (does not exist), bg-ink-500, or a new opacity variant like bg-ink-900/60 — it will keep its dark colour in light mode. Either reuse a class that is already remapped, or add a matching html[data-theme="light"] rule.

A real example of a global side effect

The nav <nav> uses bg-ink-900 so the mobile menu sheet is opaque, plus md:bg-transparent for desktop. In light mode, the !important remap turned bg-ink-900 white and beat md:bg-transparent, painting a white strip across the desktop hero. The fix is the @media (min-width: 768px) html[data-theme="light"] #primary-navigation rule with its explanatory comment. Expect this kind of interaction whenever !important remaps meet responsive utilities.

Theme switching and persistence

  1. Before paint_document.tsx inline script reads localStorage["portfolio-theme"]; anything other than "light"/"dark" means "dark".
  2. HydrateThemeProvider starts as "dark", then its effect reads storage, sets state, and sets isReady.
  3. ToggleThemeToggle calls toggleTheme() → setTheme(next).
  4. ApplyapplyThemeToDocument sets data-theme and colorScheme on <html>; storage is updated.
  5. CSS reactsAll html[data-theme=…] selectors switch instantly; body transitions colour over 0.35s.

The site does not follow the operating system preference; the default is always dark until the visitor chooses light. ThemeToggle shows a neutral circle until isReady to avoid showing the wrong icon during hydration, and SkillIcon uses the dark-background logo variant until then.

  • League Spartan and Josefin Sans are preloaded in _document.tsx; Raleway is not.

How RevealOnScroll works (animation states)

The component has three states: "hidden" → "visible" → "done".

Why the "done" state exists: many revealed elements also carry .ink-panel-hover, which has its own transition and transform. If .reveal-base (with its 0.6s transition and delay) stayed on the element, hover effects would inherit that slow, delayed transition. Removing the reveal classes after the entrance avoids conflicting transitions on the same element.

The delay classes reveal-delay-1 to reveal-delay-5 (0.08s steps) create staggered grids; components pick one with index % n.

Defined as the internal Lightbox component in components/projects/ProjectGallery.tsx and rendered in a portal at z-index: 140 above the modal (z-[100]).

Authentication and Authorization

Only Mission Control has authentication. It uses Firebase Email/Password sign-in plus a Firestore whitelist, and the real security boundary is the Firestore rules — not the hidden route.

Overview

  • Provider: Firebase Authentication, Email/Password method. There is no sign-up UI; admin users are created in the Firebase Console.
  • Authentication ("who are you?"): signInWithEmailAndPassword.
  • Authorization ("are you allowed?"): a document must exist at admins/{uid}.
  • Roles: one role — admin. No role-based permissions.
  • Public pages and API routes do not require authentication.

Login flow

  1. Form checksAdminLoginForm: honeypot empty; form open ≥ 2s; typing ≥ 0.8s; 1s double-submit guard; adminLoginSchema; at most 5 attempts per 60s per tab.

State handling and validation timing

  • All inputs are controlled by Formik (value + onChange={formik.handleChange}; the input name must match the field key).
  • validateOnChange: false and no onBlur handlers are wired, so validation runs on submit. Errors appear only after the first submit (formik.submitCount > 0) and update on the next submit, not while typing.
  • validate runs contactMessageSchema.safeParse(values) and converts issues with toFieldErrors (first message per field).
  • The form has noValidate, so browser-native validation bubbles are off even though some inputs have required.
  • Each input has aria-invalid and aria-describedby pointing to its FieldError span.

Submission, success, and errors

  1. onSubmit clears any old notice and POSTs JSON (values + honeypot) to /api/contact.
  2. The server re-validates with the same schema (never trust the browser).
  3. Success (response.ok && result.ok): helpers.resetForm() and a green .form-notice--success with role="status": "Thanks, {name}…".
  4. Server error: fieldErrors are pushed into Formik with helpers.setErrors, and an amber .form-notice with role="alert" shows the server message.
  5. Network error: "Network error. Check your connection and try again."
  6. While submitting, the button is disabled and reads "Sending…".

Anti-spam protection and email

  • Honeypot field named website (CONTACT_HONEYPOT_FIELD). If filled, the server returns success but stores nothing.
  • Rate limit: 5 per IP per 10 minutes per server instance.
  • No CAPTCHA. If you add one, verify its token on the server in pages/api/contact.ts.
  • Email: sendContactNotification sends "{name} filled the contact form on Bilal Sami" to NOTIFY_EMAIL with replyTo set to the visitor, listing only non-empty fields. Skipped when SMTP variables are missing.

Images, Assets, and File Handling

How static files are organised and served, how project screenshots become responsive WebP images and galleries, and how to add images without breaking references.

Public asset conventions

  • Everything under public/ is served from the site root. Reference files with a leading slash and without public: /icons/tech/react.svg, never public/icons/tech/react.svg or a relative path.
  • Files are not hashed or processed; replacing a file keeps its URL (browsers and the CDN may cache the old version for a while). Renaming changes the URL.
  • Paths are case-sensitive on Vercel (Linux) but not on Windows. Folder names such as JimtaDash and rbf-dash must match exactly in code.
  • Everything in public/ is downloadable by anyone, including the ten case-study source texts such as /projects/alphaDash/alpha-arc-casestudy.txt. Do not put private files there.

Image components

The project uses plain <img> elements everywhere; next/image is not used (the ESLint rule @next/next/no-img-element is turned off). Two consequences:

  • No automatic resizing or format conversion by Next.js/Vercel. Optimisation is done ahead of time by scripts (below).
  • components/Image/index.tsx is a tiny wrapper typed with next/image's props that forwards only alt, src, style, width, and height. Props such as className and loading="lazy" passed to it by floatingImages.tsx and shapes.tsx are silently dropped.

  2. Cards and spotlightgetProjectImage(project.image, "cover" | "tall") looks the path up in projectImageVariants and returns src, srcSet, width, height. If no variants exist it falls back to the original.

  4. Gallery previewShows the 1280px WebP preview; thumbnails use loading="lazy".
  5. LightboxLoads image.src — the original full-resolution PNG — so text stays sharp when zoomed. This is intentional (commit "Show full-resolution screenshots in the project lightbox without stretching them") but can mean downloads of several megabytes per image.

  • Near-black logos (Next.js, GitHub, Express, Radix, shadcn) have a srcDark light-coloured variant (*-light.svg) that SkillIcon uses in dark mode.
  • Abstract skills (Yup, Recharts, dashboards, OOP, database, performance, SEO, interests) use Font Awesome icons by name; the name must exist in utilities/resolveFontAwesomeIcon.ts.
  • Unknown keys render the generic Font Awesome "code" icon.
  • Hero badges: /assets/images/icons/react.png and complete.png locally, plus two skillicons.dev URLs (remote).

Favicons, logos, and fonts

  • public/favicon.ico (served by default) plus siteIdentity.logoImage (programmer.webp) as an icon link, the nav/footer logo, the hero art, the About image, and the Open Graph image.
  • Fonts: public/assets/fonts/*.woff2 with .ttf fallbacks, declared in globals.css.

How to add a new image without breaking references

  1. Put the file under public/ in the right folder, using lowercase-with-hyphens for new names.
  2. Reference it as /folder/file.ext — copy the path from the file tree to avoid case mistakes.
  3. Always give alt text (or alt="" if decorative), and width/height to prevent layout shift.
  4. For a project screenshot, run the scripts above so it gets WebP variants and appears in the gallery.
  5. Check it on npm run dev, then on the Vercel preview (case sensitivity shows up only there).

  • Icons: Font Awesome icons are imported individually in resolveFontAwesomeIcon.ts rather than registering whole packs.
  • Theme without flash: the inline script prevents a repaint after hydration.
  • Background noise: a 200px SVG tile rather than a full-viewport filter.
  • Reduced motion: animations and Lenis are disabled for users who ask for it.

Chapter 20 · Working on the Code

Troubleshooting and Debugging

Symptoms, likely causes, how to inspect, and safe fixes. Each entry is marked Project-specific when it comes from this codebase's actual behaviour, or General when it is a common possibility.

A general debugging method

  1. Reproduce reliably and note the exact URL, theme, width, and steps.
  2. Open DevTools: Console (errors), Network (failed requests and status codes), Elements (classes and computed styles), Application (storage).
  3. Find the code: search the repo for visible text, a class string, or an error message.
  4. Change one thing at a time; use git diff and git stash to compare with the last working state.
  5. Confirm the fix on a production build (npm run build && npm run start) when it involves performance, metadata, or hydration.

Startup, build, and module errors

The app fails to start or install General

Causes: very old or very new Node; corrupted node_modules; peer-dependency conflicts.

Inspect: node -v; read the first error in the output, not the last.

Fix: delete node_modules and reinstall with npm install (the repo's .npmrc already sets legacy-peer-deps). Use a Node LTS release.

"Module not found" General

Causes: wrong relative path (../../ depth), file renamed, letter case differs from the import (passes on Windows, fails on Vercel), or a package not installed.

Fix: this repo uses relative imports only (no path aliases in tsconfig.json). Count directory levels; match case exactly.

Build fails on Vercel but dev works Project-specific

Causes: next build runs ESLint and type checks, which next dev does not enforce. Git history shows this happened ("fix: resolve ESLint errors blocking Vercel build", "Remove orphaned portfolio carousel that broke the Vercel build").

Fix: run npm run build locally before pushing; fix the first reported error.

TypeScript errors General

Inspect: npx tsc --noEmit lists every error with file and line.

Common here: adding a project field without updating data/types.ts; misspelling a ProjectCategory or SocialPlatform value; forgetting a field in toMessage after changing the contact schema. strict mode is on, so null/undefined must be handled.

ESLint complains about component style Project-specific

The config requires arrow-function components, forbids unused variables, and runs Prettier as a rule. Run npm run lint:fix first; most issues fix themselves.

Routes, images, icons, and themes

A page shows the 404 Project-specific

Causes: the file is not directly in pages/ or its name differs from the URL; a link uses a typo instead of routePaths. For Mission Control dashboard URLs, the "404" is the masked state for anyone not verified as admin (Chapter 12).

Broken images Project-specific

Inspect: Network tab → the failing URL. Paste it into the address bar.

Causes: path includes public/; case mismatch (JimtaDash vs jimtadash); a project screenshot renamed without re-running the scripts, so projectScreenshots.ts points at a missing file (run node scripts/verify-project-galleries.js). The resume PDF is a known missing file.

A skill icon shows the generic </> symbol Project-specific

The iconKey is not in skillIconRegistry, or a Font Awesome name is not in resolveFontAwesomeIcon.ts. If a local SVG is blank, open it directly at /icons/tech/<name>.svg. If a dark logo is invisible in dark mode, add a srcDark variant.

Hero badges for Next.js/Tailwind missing Project-specific

They load from skillicons.dev. Offline, behind a blocker, or if that service is down, they disappear. Switch them to local SVGs in components/introduction/floatingImages.tsx.

Wrong colours in light mode, or the theme "flashes" Project-specific

Wrong colour: the class used is not in the light-mode remap list in globals.css. Inspect the element; if no html[data-theme="light"] rule appears for that class, add one or use a remapped class.

Flash: the inline script in _document.tsx was removed or the storage key changed. The key must be portfolio-theme in both _document.tsx and ThemeProvider.tsx.

Hydration warning about data-theme: <Html> renders data-theme="dark" and the script may change it before React hydrates. React does not hydrate <html> attributes from _document, so this is expected to be quiet; investigate only if a warning names a component.

Layout, modal, gallery, and lightbox

Horizontal scrolling or overflow on mobile General

body clips horizontal overflow, so the symptom may instead be content cut off. Use the console snippet in Chapter 7, then add min-w-0, break-words, or a smaller fixed width.

The page will not scroll after closing a menu or modal Project-specific

Cause: an overflow: hidden left on <html> or <body>. The nav, modal, lightbox, shortcuts dialog, and admin dialogs each save and restore the previous value in their effect cleanup; Lenis stops while either is hidden.

Inspect: Elements → <html> and <body> style attributes. If you add a new overlay, copy the save/restore pattern exactly.

Wheel scrolling inside a modal scrolls the page instead Project-specific

The scroll container is missing data-lenis-prevent, so Lenis intercepts the wheel. Add the attribute to the element with overflow-y-auto.

Escape closes both the lightbox and the modal Project-specific

The lightbox listener uses the capture phase and stopPropagation; the modal ignores Escape while lightboxOpenRef.current is true. If this breaks, check that onLightboxChange is still passed from ProjectDetailsModal to ProjectGallery.

Gallery shows the wrong or no extra screenshots Project-specific

The folder is derived from project.image (/projects/<folder>/…). If the image path points elsewhere, projectScreenshots[folder] is empty. Editing the gallery array in data/projects.ts has no effect — regenerate the manifest.

Lightbox image is blurry, tiny, or shakes Project-specific

Tiny: fit is capped at one source pixel per device pixel; small originals stay small by design. Slow to appear: the original PNG is large. Shaking: previously caused by scrollbars toggling; the fix is scrollbar-gutter: stable and the size check in the ResizeObserver callback — keep both.

APIs, database, auth, and environment

Contact form says "Messaging is temporarily unavailable." Project-specific

HTTP 503: FIREBASE_PROJECT_ID, FIREBASE_CLIENT_EMAIL, or FIREBASE_PRIVATE_KEY missing. Expected in local development without .env.local.

Firestore write failed. Check the server log line [contact: Firestore write failed] …. A PEM error means the private key lost its quotes or \n escapes. Wrong project id or a disabled service account are other causes.

Emails are skipped silently if any of SMTP_HOST, SMTP_USER, SMTP_PASS, NOTIFY_EMAIL is missing. Visitor emails are also skipped if the same IP was notified in the last 24 hours. Gmail requires an App Password. Look for notification email failed in logs.

See the table in Chapter 12 and the troubleshooting table in documentation/mission-control.md. Most cases are a missing admins/{uid} document or undeployed rules.

Env var change has no effect Project-specific

NEXT_PUBLIC_* values are baked in at build time: restart npm run dev locally; redeploy on Vercel. Make sure the variable is set for the right Vercel environment (Production vs Preview).

Visitor sessions show "Local / Development" or "unknown" Project-specific

Expected on localhost (no geo headers) or on hosts that do not send Vercel/Cloudflare headers.

When Should This Be Changed?

Expand a decision to see what it provides, its limits, the signal that would justify changing it, what else would be affected, and why changing it without that signal is risky.

1. Pages Router with static pre-rendering
Provides
Fast static pages, simple hosting, a mental model where every component can use hooks, and router.events for global behaviours.
Limitations
Content changes require redeploys; no Server Components; nested layouts are manual (getLayout); Next.js 13.1.6 is old.
Change when
You need many data-driven routes (a blog, per-project pages from a CMS), per-request data, or you must upgrade Next.js for security support.
Affects
_app, _document, PageShell, four router-event listeners, Mission Control layouts, ESLint config.
Risk of changing unnecessarily
Regressions in scroll restoration, menu focus, 404 behaviour, and theme flash — all of which are tuned today — for little gain on a small static site.
2. Content in typed TypeScript files
Provides
Type-checked content, Git history of every wording change, review before publish, zero runtime cost.
Limitations
Only a developer can edit; all project text ships in the JS bundle.
Change when
Non-developers need to edit, content updates become frequent, or the case-study bundle size becomes a measurable problem.
Affects
Every component importing from data/; build pipeline (data fetching at build or request time).
Risk
A CMS adds accounts, network failure modes, and loses the strict "verified facts only" review the comments describe.
3. One PageShell for metadata
Provides
Consistent titles, canonical URLs, OG/Twitter tags, and robots rules everywhere.
Limitations
One OG image for all pages unless passed; no structured data.
Change when
Adding JSON-LD, per-page share images, or migrating to the App Router metadata API.
Affects
Every page and the admin states.
Risk
Per-page copies drift apart; a broken shell breaks SEO site-wide — test View Source after edits.
4. Shared building blocks
Provides
Visual consistency and one place to fix bugs (ProjectCard fixes apply to Home and Projects).
Limitations
Wide blast radius; the modal-state pattern is duplicated in two parents rather than shared.
Change when
A page genuinely needs a different design — add a prop or a variant rather than forking.
Affects
See the reuse table in Chapter 5 and the impact map in Chapter 24.
Risk
Forking components creates drift; over-generalising them creates prop soup.
5. Dark-first classes with light remaps
Provides
Light mode was added without rewriting JSX (the CSS comment says so).
Limitations
Heavy !important; only listed classes are remapped; class names describe dark colours, not roles; has already caused one desktop-nav bug.
Change when
Styling bugs between themes become frequent, or a third theme is needed. The cleaner design is semantic tokens (bg-surface, text-muted) backed by CSS variables via Tailwind config.
Affects
Almost every component's className and the bottom half of globals.css.
Risk
A large, visual-only refactor with no tests; do it page by page with screenshots.
6. Writes only through API routes and the Admin SDK
Provides
Server-side validation, honeypot, rate limiting, and email in one place; browsers can never write directly.
Limitations
Requires a Node host (no static export); service-account secret management.
Change when
Rarely. Moving to Firebase Cloud Functions or another backend would be a hosting decision.
Affects
pages/api/*, server/*, rules, env vars.
Risk
Opening client writes in rules to "simplify" would let anyone spam or alter data.
7. Client-side admin gate backed by rules
Provides
A hidden admin with no admin API surface; data protected by Firestore.
Limitations
Dashboard routes return HTTP 200; client checks are bypassable (by design harmless because data is rules-protected).
Change when
You add admin actions that need server code (e.g. replying from the dashboard via SMTP) — then add server-side ID-token verification.
Affects
AdminAuthProvider, MissionControlLayout, rules.
Risk
Adding an unauthenticated admin API route would bypass everything.
8. Self-built visitor tracking
Provides
Owner-controlled data, no third-party scripts or cookies (only first-party browser storage), realtime per-visitor sessions, email alerts.
Limitations
No aggregate charts, funnels, or bot filtering beyond user-agent parsing; Firestore cost grows with traffic; 1,000-session dashboard cap.
Change when
You need aggregate analytics or traffic grows enough that Firestore writes per page view cost money.
Affects
VisitorTracker, the session API, the Visitors panel, the privacy expectations described in the docs.
Risk
Third-party analytics adds weight and may need consent handling.
9 & 10. Offline WebP pipeline, plain <img>, originals in the lightbox
Provides
Predictable files, no build-time image processing, no dependency on Vercel image optimisation, sharp zoom.
Limitations
Manual script runs; large repository; multi-megabyte lightbox downloads.
